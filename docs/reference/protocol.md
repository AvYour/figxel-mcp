# Bridge Protocol — Figxel

The wire-level specification for communication between Figxel's bridge (MCP server + WebSocket server, one Node process) and the Figma plugin (the `ui.html` iframe, which forwards to the `code.js` sandbox).

| | |
|---|---|
| Transport | WebSocket text frames, `ws://127.0.0.1:38452` (fixed port; `BRIDGE_PORT` is for tests only), or a team's hub at a `wss://` address (§11) |
| Encoding | UTF-8, one JSON object per frame |
| Protocol version | `1` (sent in both `hello` and `welcome`) |
| Source of truth for types | `src/shared/protocol.ts` — this document explains, the code binds |

An **op** name is the MCP tool name without the `figma_` prefix (`figma_create_frame` → `create_frame`). Full list: [tools.md](tools.md).

---

## 1. Connection Flow

```
plugin (ui.html)                          bridge
      │  1. WebSocket upgrade                │  check Origin header: must be absent or "null"
      ├─────────────────────────────────────►│  otherwise → close 4003
      │                                      │  wait for hello, max 5 s (→ 4008)
      │  2. { t:"hello", token, instanceId,  │
      │       ops[], file, page, user ... }  │
      ├─────────────────────────────────────►│  bad token → 4001
      │                                      │  unsupported protocolVersion → 4005
      │  3. { t:"welcome", sessionId,        │
      │       limits }                       │
      │◄─────────────────────────────────────┤
      │  4. selection/page events (sync)     │
      ├─────────────────────────────────────►│
      │        ...normal exchange...         │
```

Handshake rules:

1. **Origin.** Figma's plugin iframe has origin `null` (documented under "Making Network Requests"); the Node mock plugin sends no Origin at all. Any other origin (e.g. `https://any-site.example`) is closed with `4003`. This is defence in depth — **the token remains the real gate** (§7).
2. The plugin **must** send `hello` within 5 seconds; otherwise → `4008`. A second `hello` → `4002`.
3. The token is compared in constant time against the contents of `~/.figxel/token` (`$BRIDGE_HOME/token` when that is set). When `BRIDGE_HOME` is unset and that file is missing, a valid token in `~/.figma-mcp/token`, the home folder from before the rename, is copied there once at start (the copy never overwrites an existing token), so the plugin keeps working with the token it saved.
4. **One connection = one session.** `sessionId` is generated by the server per connection. `instanceId` is generated by the plugin once per plugin window and stays the same across reconnects.
5. If the same `instanceId` already has a live session (a reconnect before the heartbeat notices the old connection is dead), the old session is closed with `4004` and replaced. No duplicate ghost sessions.
6. The server records the `ops` and the `editorType` from `hello`. A tool whose op does not run in that editor, or whose write is not yet verified there, is answered `UNSUPPORTED` naming the editor and the file — checked **first**, before any `request` is sent ([spec §4.7](../superpowers/specs/2026-10-06-figma-mcp-design.md#47-editor-types)). A tool whose op is absent from the `ops` list is answered `UNSUPPORTED` with the hint "The connected plugin is older than this server: ask the user to close the Figxel plugin window and run it again (Plugins → Development → Figxel). If the op is still missing, run `npx -y figxel-mcp@latest setup` and import the plugin from the manifest it prints."

## 2. Messages: plugin → server

### `hello` (required, once)

```jsonc
{
  "t": "hello",
  "protocolVersion": 1,
  "token": "8f3c…",               // 64 hex characters (32 bytes)
  "instanceId": "6b1f…",          // created by the plugin when its window opens; stable for the window's lifetime
  "pluginVersion": "0.1.0",
  "apiVersion": "1.0.0",          // figma.apiVersion
  "editorType": "figma",          // figma.editorType: "figma", "figjam" or "slides"
  "ops": ["create_frame", "get_design_context", "…"],  // ops this plugin implements
  "file": { "name": "Landing Page", "key": null },     // figma.fileKey may be null (spec §14)
  "page": { "id": "0:1", "name": "Home" },
  "user": { "id": "12345", "name": "Alex" },           // null when the currentuser permission is absent
  "running": { "op": "export_video", "id": "r-3fa1c2d9-2", "elapsedMs": 41200 }  // or null; absent on old bundles
}
```

`running` is the op the sandbox is still running from an earlier connection. The sandbox runs one op at a time and outlives the server process that sent it, so after a reconnect — to the same hub or to a new one after the old hub exited `[C-271]` — the bridge learns that a video render holds the plugin, and answers other calls `BUSY` until the plugin answers that render, instead of queueing them behind it until they `STALL`.

`editorType` is load-bearing: the bridge decides every op against it ([spec §4.7](../superpowers/specs/2026-10-06-figma-mcp-design.md#47-editor-types)). `ops` means "implemented by this build" and is **not** filtered by editor — a board's plugin advertises the Design-only ops too, so "too old" never stands in for "wrong editor". An editor value the bridge does not run in (`dev`, `buzz`) gets every op refused except the ones the bridge answers itself. The plugin refuses the table's **no** cells again before running an op, for a hub build that predates the gate.

### `result` (the answer to a request)

```jsonc
{ "t": "result", "id": "r-17", "ok": true, "data": { /* JSON-serializable */ } }

{ "t": "result", "id": "r-17", "ok": false,
  "error": { "code": "NODE_NOT_FOUND", "message": "Node 1:99 does not exist",
             "hint": "Use figma_get_selection or figma_search_nodes" } }

// cancelled / failed midway — work already completed is still reported
{ "t": "result", "id": "r-17", "ok": false,
  "error": { "code": "CANCELLED", "message": "Cancelled (STALLED)" },
  "partial": { "created": [{ "id": "12:34", "name": "Hero", "path": "children[0]" }], "failedAt": "children[1]" } }
```

- `data` **must** be JSON-serializable. The plugin converts Figma objects (getters, cyclic references) into a DTO before sending.
- Write-op results carry `idempotencyKey` and, when served from cache, `"replayed": true`.
- **Binary data** (export) is sent as `{ "mime": "image/png", "bytes": 184320, "base64": "…" }`. The plugin never writes files — the bridge does (§3, `request`).
- **Large binary payloads** (base64 > 8 MB) are sent in chunks: a `result` carrying `{ mime, bytes, chunks: N }` with no `base64`, followed by N `chunk` frames. Nothing is rejected for being too large. The bridge decodes each chunk as it arrives and keeps an export's bytes as binary, never as one long base64 string.

### `chunk` (continuation of a binary payload)

```jsonc
{ "t": "chunk", "id": "r-17", "seq": 0, "base64": "…" }   // seq 0..N-1, in order
```

Every `chunk` resets its request's idle timer. The bridge reassembles after the final chunk.

### `progress` (required for long ops)

```jsonc
{ "t": "progress", "id": "r-17", "done": 1500, "total": 8000, "phase": "creating nodes" }
```

- An op that may run > ~5 seconds **must** send `progress` **at least once per second**, and **at most once per 250 ms** (the plugin throttles; a 12 ms yield must not mean 83 messages per second).
- `progress` is the only "still alive" signal for a request (§4). A silent op is treated as stalled.
- `total` is optional (it is not always known up front).

### `event` (push, unsolicited)

```jsonc
{ "t": "event", "name": "selection_changed", "data": { "nodeIds": ["1:2","1:3"], "count": 2, "at": 1759714440123 } }
{ "t": "event", "name": "page_changed",      "data": { "pageId": "0:2", "pageName": "Components" } }
{ "t": "event", "name": "nodes_changed",     "data": { "count": 4, "nodeIds": ["1:2"], "at": 1759714440123 } }
```

- `nodes_changed` comes from `figma.currentPage.on("nodechange")` — **not** `figma.on("documentchange")`, because under `documentAccess: "dynamic-page"` that event requires `loadAllPagesAsync()` (expensive in large files). The listener is re-attached on every `page_changed`. `nodeIds` is truncated to 50.
- Events are debounced by 150 ms.
- Events are **observational only**: stored as the session's latest state (read via `figma_status` / `figma_get_selection`), never triggering a tool call.

### `log` (plugin diagnostics → bridge stderr)

```jsonc
{ "t": "log", "level": "info", "message": "Font fallback: Inter → Roboto" }   // level: debug | info | warn | error
```

### `pong`

```jsonc
{ "t": "pong", "at": 1759714475012 }
```

## 3. Messages: server → plugin

### `welcome`

```jsonc
{
  "t": "welcome",
  "sessionId": "s-3",
  "serverVersion": "0.1.0",
  "protocolVersion": 1,
  "person": "alice",          // only from a team's hub (§11): whose token this is
  "limits": {
    "maxQueueDepth": 32,
    "idleTimeoutMs": 30000,
    "exportIdleTimeoutMs": 120000,
    "heartbeatMs": 15000,
    "maxFrameBytes": 33554432,
    "chunkBytes": 8388608
  }
}
```

### `request`

```jsonc
{ "t": "request", "id": "r-17", "op": "create_frame",
  "params": { "name": "Hero", "width": 1200, "height": 600 },
  "idleTimeoutMs": 30000,
  "idempotencyKey": "landing-hero-v1" }      // document-write ops only
```

- `id` is unique across bridge processes, formatted `r-<prefix>-<n>`: 8 hex characters chosen at random when the process starts, then a counter. With `r-<n>` alone a new hub started again at `r-1`, and an old render's `result` answered the new hub's request that carried the same id.
- `idleTimeoutMs` measures **idle**, not a duration ceiling (§4).
- Bridge-only parameters are **not** forwarded to the plugin. Example: `saveTo` on `figma_export_node` is held by the bridge; the plugin receives only `{ nodeId, format, scale }` and returns bytes; the bridge validates the path and writes the file.
- **Sequential per session.** The bridge does not send a new request to a session before the previous request's `result` arrives. The per-session queue holds 32; beyond that → `BUSY` (§4). While a video render holds the plugin (`export_video` sent and not yet answered, or waiting in the queue), a new request is not queued: it is refused at once with `BUSY` (§4).

#### Idempotency

`idempotencyKey` is present on every document-write request (the `create`, `modify`, `style`, and `eval` groups). Its source is the agent's `idempotencyKey` parameter, or one generated by the bridge (`k-<uuid>`) when the agent supplies none. The key is always returned in results **and** errors, so the agent can retry safely.

`guard` is present on every document-write request from a current server: `{ conflicts, force, agent }`. `conflicts` is the server's `BRIDGE_CONFLICTS` (`refuse`, `warn`, `off`) and `force` the call's own; with `refuse` and no `force` the plugin answers `STALE` before the op runs when someone else changed a target after the agent last read or wrote it, and with `warn` it runs the op and adds `conflicts` to the result. `agent` names the server process that sent the write — a proxy's guard passes through the hub unchanged — so `rollback` can refuse to undo another agent's calls (`ROLLBACK_BLOCKED`). A request without `guard`, from an older server, is never refused for a conflict.

The plugin keeps a `Map<key, entry>` in sandbox memory:

| Key status when the request arrives | Plugin behaviour |
|---|---|
| Unknown | Execute; record `running` |
| `running` (an op with the same key is still in flight) | **Attach:** do not execute again; also send a `result` for this id when the op finishes |
| `done` (≤ 15 minutes, LRU of 1000 entries) | Reply immediately with the stored result plus `"replayed": true` |
| Reused for a different op | `INVALID_PARAM` — "idempotencyKey already used for op `<op>`" |

The bridge does the same on its side: a second tool call with a key whose request is still in flight simply awaits the same promise, without sending a new frame.

- The map lives in the **sandbox**, so it survives WebSocket disconnects and bridge restarts. It is lost when the plugin closes — and if the plugin closes mid-op, the outcome of that op is unknown. The agent must inspect the canvas (`figma_search_nodes`) before retrying in that case.
- Only a summary of the result is stored (ids, names), not export bytes.
- Read ops carry no key — they are naturally idempotent.
- **A failure that provably changed nothing is not recorded.** An op that fails before touching the document says so with `partial: { created: [] }`; the plugin then forgets the key instead of storing the error, so a corrected retry under the same key runs rather than replaying the refusal. Every other outcome — success, or a failure that may have changed something — is recorded.

#### Motion plans in the file

`set_motion_plan` stores a plan the server has already checked; the plugin only stores it, so its params are the record itself:

```jsonc
{ "t": "request", "id": "r-21", "op": "set_motion_plan",
  "params": { "nodeId": "12:34",
              "plan": { "v": 1, "brief": { "audience": "…", "message": "…", "format": "1080x1920 Reels", "durationS": 6, "fps": 30 },
                        "beats": [{ "name": "hook", "from": 0, "to": 1.5, "onScreen": "…", "action": "…", "transition": "…" }] } },
  "idempotencyKey": "plan-hero-v1" }
```

- The plugin finds the node's top-level frame by walking parents, checks that `brandId` and `ctaId` (when present) are inside it (the frame compared as a layer, so a second handle of it counts `[C-199]`), and writes `JSON.stringify(plan)` with `setSharedPluginData("figmamcp", "motionPlan", …)` on the frame, the namespace the storyboard record uses, readable by any plugin. Every check runs before that one write (`partial: { created: [] }` on a refusal). The result is `{ frameId, frameName, replaced, warnings? }`. While the frame has second ids `[C-199]` (its page lists it under a second id too, or the layer's parents lead to another handle of it), a warning names a `brandId` or `ctaId` given as the id a listing showed, which stops resolving when that ends; and when the page lists the frame twice, a warning names both ids and says to use the one its create call returned.
- `get_motion_context` reads the plans back: `scope.topLevelFrameIds` (the frame around each scope root, or null) and `motionPlans` (`[{ frameId, name, plan | null, invalid? }]`).
- `check_motion`'s snapshot carries the plan of the frame it read, in the same pass: `plan` (null when it has none) and `planInvalid?`, so `figma_check_motion` is judged against that frame's own plan.
- `check_motion` also takes `resolveIds?` (the `brandId` and `ctaId` the call names) and answers `aliases`, `unmapped?`, `outside?` and `gone?` for them and for the plan's `[C-199]`: `aliases` maps each named id the walk did not read under its own id to the one listed layer that is it (`{}` when there is none); `unmapped` names those two or more listed layers match (same type, name and box); `outside` names those that are in no layer of this frame, given only when the walk read the whole frame; `gone` names ids that resolve to nothing. A layer past a `maxNodes` cut is in none of them. When the page lists the frame under more than one id, `root.handles` gives them all, its own first. The server judges the plan as the snapshot lists it, words a missing layer by these fields, and records a passing check under every id in `root.handles`.
- Before a keyframe write or a final render, the server's motion gate (`BRIDGE_PROCESS`) sends one `get_motion_context` request with `{ nodeId, recursive: false, maxNodes: 1 }` to learn the frame and its plan. When the process wants a step first, the server answers the tool call itself with `PROCESS_REQUIRED` (§9) and sends nothing else.

### `cancel`

```jsonc
{ "t": "cancel", "id": "r-17", "reason": "STALLED" }   // STALLED | CLIENT_CANCELLED | SHUTDOWN
```

- The plugin stops at its **next yield point** and replies `result` with `ok:false`, `code: "CANCELLED"` plus `partial`. Changes already applied are not rolled back.
- If other requests are attached to the same op, the op continues; only the cancelled request is detached.
- Ops with no yield point (a single host call such as `exportAsync`) cannot be interrupted; they finish, and the bridge ignores a `result` arriving for an id it is no longer waiting on — but the outcome is still recorded in the idempotency map.

### `ping`

```jsonc
{ "t": "ping", "at": 1759714475000 }   // every 15 s
```

## 4. Timeout — Activity-Based, Not Wall-Clock

A wall-clock timeout is a hard limit in disguise: "max 30 seconds per request" means a 4-minute job is **rejected** — exactly the kind of rejection this project exists to remove. So the bridge measures **silence**, not **duration**.

| Timer | Default | Reset by | On expiry |
|---|---|---|---|
| Per-request idle | 30 s (export ops: 120 s; `export_video`: none) | every `progress` / `chunk` for that id | `cancel{reason:"STALLED"}` to the plugin; the tool call is answered with a `STALLED` error |
| Hello | 5 s | — | close `4008` |
| Heartbeat | `ping` every 15 s | **any** message from the plugin | 45 s of silence → connection closed, session dropped, pending requests → `NO_SESSION` |
| Total duration in the bridge | **none** | — | — |

- **An op that keeps reporting is never stopped by the bridge**, however many hours it runs.
- **An op that is genuinely stuck is still detected** within 30 seconds of its last report.
- Export ops get a 120 s idle because `exportAsync` is a single host call that cannot report progress midway.
- A video render (`export_video`) gets no idle limit. One `exportAsync` renders the whole video, a minimized Figma window can hold it for 40 minutes and then finish it `[C-198]`, and `figma_export_video` runs it as a job detached from the call `[C-249]`: a `STALLED` there threw the late result away while the plugin stayed busy anyway. A plugin that is gone is still caught, by the socket closing or by the heartbeat — the plugin window answers `ping` while the sandbox renders.
- `idleTimeoutMs` can be raised per request by specific tools (e.g. `figma_eval` via its `timeoutMs` parameter), but the meaning stays idle.

### A limit outside the bridge's control: the MCP client timeout

The bridge imposes no duration limit — **but an MCP client may.** This is a real limit the operator must know about:

| Client | Behaviour (checked 2026-10-06) | How to loosen it |
|---|---|---|
| Hermes v0.21.5 | Tool-call timeout defaults to **300 s wall-clock** (`_DEFAULT_TOOL_TIMEOUT` in `tools/mcp_tool_common.py`); `call_tool` is invoked without a progress callback, so progress does **not** extend it | `mcp_servers.figxel.timeout` in the Hermes config (the key is the name the server was registered under) (`hermes config path` for its location). Accepts up to **~49.7 days on Windows** — a semantic "unbounded" (`MAX_SAFE_TIMEOUT_S`, `agent/deadline.py`) |
| Clients built on the MCP TypeScript SDK `[C-030]` | 60 s default per request; extended by progress only when the client uses `resetTimeoutOnProgress` | Each client's own configuration |
| Other clients | Varies | Check their documentation |

If the client gives up first: (a) if it sends `notifications/cancelled`, the bridge forwards `cancel{reason:"CLIENT_CANCELLED"}` and the partial result is stored in the idempotency map; (b) if not, the plugin finishes the op and the result is stored. Either way, **an agent retrying with the same `idempotencyKey` gets the result without duplication** — which is why the agent should supply its own key for large ops.

A client may also restart the server after its calls time out: the Claude desktop app closed the server's stdin about 2 s after three of its calls timed out, and a hub that exits takes its proxies' in-flight calls with it `[C-271]`. That is why no call waits silently behind a video render (below).

### Other conditions

| Condition | Bridge | Plugin |
|---|---|---|
| Session queue > 32 | Reject new requests with `BUSY`, gone as soon as the queue drains | — |
| A video render holds the plugin: `export_video` sent and not yet answered by the plugin (also after a cancel, or after the plugin reconnected), named as `running` in the plugin's `hello` (sent by an earlier server process), or waiting in the queue | Reject new requests with `BUSY` at once, before anything is sent. The message names the render's `jobId` and elapsed seconds, and says why it holds the plugin: running, cancelled, or no result yet from an earlier process; nothing ran, so a retry is safe (a write with the same `idempotencyKey`). After 5 min the hint says that closing and re-running the plugin ends the wait. Gone when the plugin answers the render `[C-197]` `[C-198]` | Renders on: a cancel cannot stop `exportAsync` |
| Figma ends a render in its time limit (`TIMEOUT`) | Counts the timeouts in a row per plugin window (`instanceId`); a render the plugin answers successfully resets it. The second in a row, or a timeout of a small render (the plugin sends the render's size in `partial.render`), gets a hint to restart Figma `[C-318]` | Sends `TIMEOUT`, with `partial.render: { frames, width, height }` when it knows them |
| A call `STALLED`, and the plugin has answered nothing since it connected | The hint adds that the plugin may still be finishing an op an earlier Figxel process sent it, such as a render | Runs one op at a time and outlives the process that sent it |
| Plugin disconnects with requests pending | All pending → `NO_SESSION` + `idempotencyKey` + a suggestion to retry | Reconnect (§5); an op already running in the sandbox keeps running and is recorded |
| Tool call with no session | Wait up to `BRIDGE_SESSION_WAIT_MS` (5 s) for a reconnecting plugin; then `NO_SESSION` (auto-launch was removed on 2026-10-07, spec ADR #32) | — |

`BUSY` is **back-pressure**, not a quota: there is no counter that refills over time as with a rate limit. It is the only load-based rejection, and every cause of it is temporary.

## 5. Reconnect

```
connect → hello → welcome → (normal) → disconnect
   ↑                                      │
   └── backoff: 0.5 s, 1 s, 2 s, 3 s, 3 s, … (cap 3 s) ←┘
```

- The cap is 3 s (not 10 s) because a refused loopback connection is cheap, and a fresh bridge usually appears exactly when the agent starts a session — the plugin must connect before `BRIDGE_SESSION_WAIT_MS` (5 s) expires.
- The backoff resets to 0.5 s after a connection has been stable for > 30 s.
- Once connected, the plugin sends `hello` (with current file/page) followed by `selection_changed` + `page_changed` so the bridge's state is not stale.
- **The bridge does not resend lost requests.** The agent decides to retry, and idempotency (§3) makes that retry safe.
- Close codes that **stop** the loop and show a reason in the plugin UI: `4001` (show the token form), `4003`, `4005` (show "plugin/bridge version mismatch"), `4004` (another plugin window took over).
- Close `4010` (bridge shut down cleanly) and network errors → keep retrying. The next bridge appears when the agent starts a session again.
- To a team's hub (§11) the backoff is 1 s, 2 s, 5 s, 10 s, 30 s (cap 30 s): a hub is reached over the internet and is not started by the agent, so there is nothing to race.

## 6. WebSocket Close Codes

| Code | Name | Meaning | Plugin |
|---|---|---|---|
| `1000` | normal | Normal closure | — |
| `1001` | going away | Plugin window closed | — |
| `1009` | message too big | Frame > `maxFrameBytes` (should not happen — large payloads must be chunked). Between server processes a hub sends a large result in pieces too, to a proxy that offers them (spec §4.2) | Report a bug |
| `4001` | `AUTH_FAILED` | Wrong or empty token | Stop; show the token form |
| `4002` | `DUPLICATE_HELLO` | `hello` sent more than once | Report a bug |
| `4003` | `FORBIDDEN_ORIGIN` | Origin is not `null`/absent | Stop |
| `4004` | `SESSION_REPLACED` | The same `instanceId` opened a new connection | Stop |
| `4005` | `PROTOCOL_MISMATCH` | `protocolVersion` unsupported | Stop; show the version |
| `4008` | `HELLO_TIMEOUT` | 5 s without `hello` | Retry |
| `4010` | `SERVER_SHUTDOWN` | Bridge shut down cleanly (MCP client closed stdin) | Retry with backoff |

## 7. Protocol Security Notes

- **The token is the only real gate.** Every sandbox iframe has origin `null`, so the Origin filter (§1) only screens out ordinary web pages — it does not prove that the connection is our plugin.
- Constant-time token comparison: SHA-256 both sides, then `crypto.timingSafeEqual` (that function throws when lengths differ; hashing equalises length and does not leak the token's length).
- On a laptop, bind **only** to `127.0.0.1`; there is no option to change that. `figxel-mcp hub` alone takes `BRIDGE_HUB_BIND`, for a container that only its TLS proxy reaches (§11, spec ADR #44).
- The WebSocket server's `maxPayload` is 32 MB. Larger binary payloads use `chunk` (§2).
- The bridge never sends token contents to the MCP client — only `tokenPresent` + `tokenPath`.
- By default the bridge does not log write-op `params` (they may contain client content); only `op`, `id`, duration, and size.

## 8. Full Session Example

```jsonc
// plugin → bridge: handshake
{"t":"hello","protocolVersion":1,"token":"8f3c…","instanceId":"6b1f…","pluginVersion":"0.1.0","apiVersion":"1.0.0",
 "editorType":"figma","ops":["get_design_context","create_frame","export_node","…"],
 "file":{"name":"Landing Page","key":null},"page":{"id":"0:1","name":"Home"},"user":{"id":"12345","name":"Alex"}}

// bridge → plugin
{"t":"welcome","sessionId":"s-1","serverVersion":"0.1.0","protocolVersion":1,
 "limits":{"maxQueueDepth":32,"idleTimeoutMs":30000,"exportIdleTimeoutMs":120000,"heartbeatMs":15000,
           "maxFrameBytes":33554432,"chunkBytes":8388608}}

// plugin → bridge: state sync
{"t":"event","name":"selection_changed","data":{"nodeIds":[],"count":0,"at":1759714440000}}

// agent: figma_create_frame {name:"Hero", width:1200, height:600}  (no key → the bridge generates one)
{"t":"request","id":"r-1","op":"create_frame","params":{"name":"Hero","width":1200,"height":600},
 "idleTimeoutMs":30000,"idempotencyKey":"k-0b7e…"}
{"t":"result","id":"r-1","ok":true,"data":{"id":"12:34","name":"Hero","width":1200,"height":600,"x":0,"y":0,
 "idempotencyKey":"k-0b7e…"}}

// agent: figma_export_node {nodeId:"12:34", format:"PNG", scale:2, saveTo:"hero.png"}
// saveTo is held by the bridge — the plugin receives only nodeId/format/scale
{"t":"request","id":"r-2","op":"export_node","params":{"nodeId":"12:34","format":"PNG","scale":2},"idleTimeoutMs":120000}
{"t":"result","id":"r-2","ok":true,"data":{"mime":"image/png","bytes":184320,"base64":"iVBORw0KGgo…"}}
```

## 9. Mapping to MCP (client-visible)

| Event | What the bridge does on the MCP side |
|---|---|
| `progress` from the plugin, request carries `_meta.progressToken` | `notifications/progress` (`progress`, `total`, `message`) |
| `progress`, request without a `progressToken` | `notifications/message` at level `info`, **at most 1 per 5 s** (a fallback, so logs are not flooded) |
| Client sends `notifications/cancelled` (SDK: `extra.signal` aborted) | `cancel{reason:"CLIENT_CANCELLED"}` to the plugin |
| `log` from the plugin | stderr; plus `notifications/message` at the matching level (`debug`/`info`/`warning`/`error`) |
| A tool call that skips a step of the motion process (`BRIDGE_PROCESS=strict`) | Answered by the server with `PROCESS_REQUIRED` (`partial: { created: [], missing }`, `safeToRetry: true`) and the calls that satisfy it; no `request` is sent ([spec §10](../superpowers/specs/2026-10-06-figma-mcp-design.md#10-error-handling)) |
| `event` from the plugin | Stored as state; read via `figma_status` / `figma_get_selection` (also exposed as the MCP resource `figxel://session/<id>/selection`) |
| Final `result` | A `tools/call` response. Errors become `isError: true` with the text `"<CODE>: <message>\n<hint>"` plus `structuredContent` carrying `{ code, hint, idempotencyKey?, partial? }` |

Progress rules:

1. **Coalescing.** At most 10 notifications/second to the client: keep the newest value, send every 100 ms, and **always** send the final value before the `result`.
2. **Monotonically increasing** (an MCP requirement `[C-029]`). When the plugin reports a lower value (a new phase), the bridge sends `max(previous + 1, new value)`.
3. **Stop after completion.** No progress notifications after the response is sent.

Progress only extends a tool call's life in clients that **use** it (§4). In clients that do not, the safeguard is `idempotencyKey`, not progress.

## 10. Protocol Evolution

- `protocolVersion` is raised **only** for breaking changes. The bridge accepts exactly the version it knows; anything else gets `4005`.
- New optional fields do not raise the version; receivers must ignore unknown fields.
- The plugin advertises its `ops` in `hello`; the bridge answers `UNSUPPORTED` for a tool whose op is missing (plugin older than bridge). Conversely, a plugin op the bridge does not recognise is ignored.
- `set_motion_plan` (2026-10-14) is a new op: for a plugin built before it, the bridge answers `UNSUPPORTED` as "older than this server" (the op is missing from its `ops`), and that plugin's `get_motion_context` answers without `scope.topLevelFrameIds`, which the motion gate reports the same way; its `check_motion` answers without `plan`, which the check reads as no plan. Both are additions, so `protocolVersion` stayed 1; `PROCESS_REQUIRED` never travels on the wire.
- `check_motion`'s `resolveIds`, `aliases`, `unmapped`, `outside`, `gone` and `root.handles` (2026-10-21) are additions too: a plugin built before them ignores `resolveIds` and answers without any of them, and the server then says a plugin re-run may be due when a plan's layer is missing; its `set_motion_plan` answers without `warnings`.
- `UNSUPPORTED` also covers the editor: an op that does not run, or is not yet verified, in the session's `editorType` is refused before the ops check, with `partial: { created: [] }` on a write (spec §4.7). Widening the plugin to FigJam and Figma Slides changed no message, so `protocolVersion` stayed 1; `editorType` was in `hello` from the start.

## 11. A Team's Hub

`figxel-mcp hub` runs the bridge on a server as a pure relay, behind a TLS proxy ([docs/hub.md](../hub.md), spec ADR #44). The frames are the ones above; what changes is who may connect and what each one sees.

- **A token names a person.** The hub reads a table of people, each with the SHA-256 of their own token, instead of one token file. A plugin's `hello` and a server process's `peer-hello` carry that person's token, and the connection belongs to that person. The comparison is the constant-time one of §7, against every entry.
- **Refused tokens are limited per address.** After 20 refused tokens from one address within 10 minutes, connections from it are closed with `4001` before their `hello` is read, for 15 minutes. The address is the last `X-Forwarded-For` entry when the socket comes from a private address (the TLS proxy beside the hub), else the socket's own `[C-408]`.
- **An unknown token learns nothing.** A plugin is closed with `4001`, as on a laptop. A server process is closed with `4001` too, without the `peer-refused` frame a laptop's hub sends (which names the hub's process id and token file). The hub's own token is random and in no table.
- **`welcome` names the person** (`person`), so the plugin window shows "as <name>". A laptop's bridge sends no `person`.
- **Each person sees their own.** A process's calls, session lookups, session waits and status requests are answered from its person's sessions only: another person's session, by id or by file name, gets the same `NO_SESSION` text as one that never existed. Idempotency keys are kept per person, so two people's identical keys run twice. A status shows the person's own sessions and server processes, and no refused-token history. `peer-welcome` carries `hubPid: 0` and `person`, the name the token stands for, which `figma_status` and `figxel-mcp join` show.
- **Revocation.** The hub reads the table again when it changes; a removed person's plugin sessions and server processes are closed with `4001` at once.
- **A server process joins by address.** With `BRIDGE_HUB_URL` set it dials that address (`wss://`, or `ws://` to loopback only), never binds the port and never becomes a hub. The handshake may take 10 s; a failed join is retried after 1 s, 2 s, 5 s, 10 s, then every 30 s.
- **One release apart.** The peer protocol stays at version 1; abilities are added as `features` and optional fields. A hub forwards an op its catalog does not know to the plugin, which decides, and treats it as a write when the proxy sent an idempotency key or a guard, so a newer write op keeps both.
- **A ping on every socket.** The hub pings each plugin with the `ping` frame of §3 and each server process with a WebSocket ping, every heartbeat. A server process also pings the hub every 30 s and lets go of a hub that has not answered for 75 s (2.5 intervals), then joins again. Proxies on the way therefore never see an idle socket `[C-405]`.
- **Origin.** The rule of §1 is unchanged: no Origin, or `null`. A proxy in front of the hub must not add one `[C-408]`.

## 12. The Web Endpoint

With `BRIDGE_HUB_WEB=1`, `figxel-mcp hub` also answers plain HTTP on its port ([docs/hub.md § Web clients](../hub.md#web-clients)). Everything else on that port still gets `426`.

- **`/mcp`** is MCP over Streamable HTTP. Every request carries `Authorization: Bearer <token>`; without it, or with a token not in the table, the answer is `401` with `WWW-Authenticate: Bearer`, and from an address turned away (§11) `429`. A request without `mcp-session-id` must be `initialize`; it opens a session whose tools join this hub over loopback as the token's person, so §11's isolation applies. A session id with another token, or one that ended, gets `404`.
- **Results** whose text or structured content names a file in the person's folder (`<home>/web/<name>`) get `downloads: [{ path, url, expiresAt }]`, added to the JSON (or as lines below plain text).
- **`GET /files/<id>/<name>`** serves such a file until `expiresAt` (an hour), and only while its real path, `..` and links resolved, is inside the person's folder; the 128-bit id is the only key, so the link works in a browser. After that, `404`.
- **`POST /files?name=<file>`**, signed in, saves the body (at most 25 MB) as `uploads/<random>-<file>` in the person's folder and answers `{ path, bytes, expiresAt }`; `path` is relative to the folder, as an import's `path` is.
- **OAuth** `[C-414]`: `GET /.well-known/oauth-protected-resource` (also with `/mcp` appended) names this server's `resource`, `<public address>/mcp`, and itself as the authorization server; `GET /.well-known/oauth-authorization-server` advertises `/authorize`, `/token`, `/register`, PKCE `S256` only, public clients (`none`) and Client ID Metadata Documents. `POST /register` takes `redirect_uris` (https, or http on localhost, on a host `BRIDGE_HUB_REDIRECT_HOSTS` allows) and answers a `client_id`, at most 20 per address an hour. A metadata document is fetched at most 30 times per address in 10 minutes, and only from public addresses. `GET /authorize` shows the sign-in page; its `POST` with the person's invite or token redirects to the registered `redirect_uri` with `code`, `state` and `iss`. `POST /token` takes `authorization_code` (with `code_verifier`) or `refresh_token`, and answers an `fxa_` access token for an hour and an `fxr_` refresh token for 30 days, rotated on each use. A `401` on `/mcp` names the metadata in `WWW-Authenticate`. An access token is good while its person's table entry is the one it was issued for.
- **Sign-in with an account** `[C-415]` `[C-418]`: the sign-in page holds the request under an id (`p`); `GET /login/figma?p=` or `/login/google?p=` goes to the provider with its own state and PKCE, and `GET /login/<provider>/callback` learns who signed in and completes the app's request (or approves a plugin's code). An invite posts `p` and `credential` to `/authorize`.
- **A remembered browser:** a sign-in sets `__Host-figxel` (HttpOnly, Secure, SameSite=Lax, 30 days); with it, the sign-in page offers **Continue as <person>**, a POST of `p` and `continue=1` to `/authorize`, and `GET /login/switch?p=` forgets it. A POST to `/authorize` whose Origin is another site is refused.
- **The plugin's browser sign-in** (a device flow): `POST /device/code` answers `device_code`, `user_code` (`XXXX-XXXX`), `verification_uri_complete` and `interval`; the plugin opens that page (`figma.openExternal` `[C-417]`) and polls `POST /device/token` with `device_code`, answered `authorization_pending` until the person signed in on `GET /device?code=`, then once `{ token, person }`: the plugin's own credential, presented in `hello` like a token, good while the person's table entry is. Both are open to the plugin's origin (CORS).
- **Limits:** an MCP message of at most 4 MB; 8 open sessions per person, the oldest closed first; a session idle for 30 minutes closes; files older than an hour are deleted.
