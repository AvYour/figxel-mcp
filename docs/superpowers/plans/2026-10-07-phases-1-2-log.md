## Audit of the first write-tool pass (2026-10-07)

| Found | Fix | Proof |
|---|---|---|
| `create_from_spec` declares `spec` as a JSON string (a recursive object schema is not portable) but forwarded the string; the plugin rejected every call | the server parses it (`parseSpecParam`), INVALID_PARAM on bad JSON before the plugin is asked | `test/write-tools.test.ts` |
| A build failing mid-way left nodes on the canvas that the error did not name | the tree is validated before anything is built; nodes are recorded pre-order the moment they exist; failures carry `partial.created` + `partial.failedAt` | `test/create-from-spec.test.ts`; live: `reported=2, unreported=0` |
| A failure that changed nothing was stored under its `idempotencyKey`, so a corrected retry with the same key replayed the old error | `changedNothing()` → `abandon(key)`: only failures that touched the canvas are remembered | `test/create-from-spec.test.ts` |
| The plugin window painted "Replaced" over a healthy connection when a superseded socket closed late | a socket's `onclose` is ignored unless it is still the current one | `test/plugin-bundle.test.ts` (failed before the fix) |
| A nested layout frame with no `background` kept `createFrame()`'s white fill — seen only by looking at a `figma_export_node` render, which no test did | a frame inside another frame starts transparent; one directly on a page or section keeps Figma's white | `test/create-from-spec.test.ts`; live: the white box behind the chips is gone |
| `create_frame` / `create_text` / `create_rectangle` / `create_ellipse` created the node, then checked `parentId`, colours, size and font — a failed check left an unreported node | every check runs before the node exists (`beforeCreating`), and the failure says `created: []` | `test/create-from-spec.test.ts` (10 red, then green); live: below |

## From Claude Code, after the restart (2026-10-07)

The first session to use the tools through a real client rather than a script. This session was a proxy sharing Claude Desktop's hub; 49 tools registered.

| Check | Result |
|---|---|
| `create_from_spec` card, then `figma_export_node` at scale 2 | the model received and read the PNG — which is how the white-box bug above was found |
| Same card after re-running the plugin | nested row transparent |
| `figma_create_rectangle` with `parentId: "404:404"` | `NODE_NOT_FOUND`; `figma_search_nodes` finds nothing left behind |
| The same `idempotencyKey`, corrected call | executed (not a replayed error): a failure that changed nothing does not pin its key |

Lesson: Figma does not reload a development plugin when `dist/plugin/code.js` changes. After every build the plugin must be closed and run again, and `figma_status` cannot yet tell a stale plugin from a fresh one (`opsAdvertised` only changes when the op list does).

## Known limits

- A result forwarded from the hub to a proxy travels as one WebSocket frame; an export whose base64 exceeds `maxFrameBytes` (32 MB, about a 24 MB image) would fail on that hop. The plugin → hub hop is chunked. Not seen in practice; fix by chunking peer `call-result` the same way if it ever is.
- `figma_set_fills` takes one object per fill with separate optional fields (`color` | `r/g/b/a` | `gradient`) instead of tools.md's "hex / {r,g,b,a} / gradient" union, because `anyOf` is not portable across providers. The plugin enforces exactly one form per entry.
